# Phase 0 baseline, 2026-11-05

Current-source build and all seven available local suites pass. The clearest
performance finding is continuous rendering while the launcher appears idle:
an invisible navigation indicator still has a running animation. Disabling
animations eliminated continuous idle frames in a diagnostic run.

Follow-up: [the first Phase 1 fix and its measurements](phase1-idle-animation.md).

No production implementation changes were made. Added artifacts are diagnostic
tools, this report, the agreed development plan, and animation research.

## Release process measurements

Three sequential runs per library, fresh application settings/cache for every
process. The operating system's filesystem cache was not flushed. All fixtures
have two synthetic offline accounts with local skin data and no real credentials.
The large fixture has 250 instances with 100 minimal Fabric mod jars each;
identical files are hard-linked across instances. Worlds and real game data are
absent. Screenshots exist in fixture folders, but default presentation uses the
generated card/banner artwork rather than exercising a large artwork collection.

| Synthetic library | First-render proxy, median (range) | Idle RSS, median across runs | Idle process CPU, median (range) |
| --- | --- | --- | --- |
| Empty instance list | 350 ms (311–390) | 301.8 MiB | 2.90% (2.89–4.69) |
| 10 instances × 25 mods | 551 ms (336–1012) | 306.1 MiB | 6.58% (6.13–7.21) |
| 250 instances × 100 mods | 702 ms (664–747) | 322.9 MiB | 6.13% (3.26–6.49) |

CPU percentages use **one fully occupied core = 100%**, not the entire 24-thread
machine. They exclude subprocess CPU, compositor CPU, and GPU work. Idle sampling
covers approximately 3–5.8 seconds after process creation: exploratory evidence,
not a long-term idle guarantee. RSS is resident process memory, not total private
allocation or GPU memory. The startup proxy ends at Qt's first rendered-frame log;
it does not establish input readiness or actual display presentation.

The raw logs, process samples and screenshots stayed local and are not kept. The final
diagnostic runner also passed end to end. Its additional small-library release run measured
343 ms to first render and 306.9 MiB idle RSS.

## Findings to prioritize

### 1. Inactive animation causes continuous idle rendering

Every initial release run logged approximately 175–177 frames during the 2.8-second
idle observation window. The small-library probe found a running
`QQuickSequentialAnimation` in `NavigationRail.qml` whose immediate indicator
parent was invisible. The surrounding navigation button remained visible.

The relevant binding is `running: Colors.animations && parent.visible`. Its
observed behavior does not gate execution on the indicator's effective activity.
Use an explicitly identified indicator/activity/window condition when addressing
this; verify the actual runtime binding rather than assuming lexical `parent`
resolves to the intended object.
[NavigationRail](../qml/shell/NavigationRail.qml#L99)

A separate uninstrumented small-library run with `interface/animations=false`
logged **zero frames** in the same idle window. Process CPU accumulated no
additional measurable clock ticks in that short sample. This supports animation
activity as the immediate source of continuous rendering; it does not prove that
all remaining background work is absent or that GPU use is zero.

Recommended first implementation: correct inactive animation gating while
retaining animations for active, visible states. Check ordinary idle, an active
game indicator, reduced motion, and hide/show transitions.

### 2. Page creation and large-library refresh can stall the event loop

The sequential large-library probe observed these synchronous calls:

| Operation | Call duration | Time from action start to first subsequent rendered-frame log |
| --- | --- | --- |
| Enter library | 108 ms | 135 ms |
| Enter settings | 58 ms | 68 ms |
| Open instance mods | 48 ms | 53 ms |
| Reload library | 55 ms | 59 ms |

The account-page visit also produced a 206 ms event-loop gap and a 209 ms
subsequent frame interval. The fixture exercises the 3D skin preview. This single
run does not isolate QML creation, shader/mesh preparation, driver work, and
scheduling; a focused trace is needed before assigning the delay to a subsystem.

`InstanceModel::reload()` synchronously reads instances, resets the model, rebuilds
file watchers, and emits updates. `allInstances()` repeatedly calls a lookup per
instance, and Home enumerates save directories. These are source-based candidates
to investigate, not individually proven causes of the full observed delay.
[Instance model](../src/core/library/instancemodel.cpp#L21),
[library queries](../src/core/library/libraryqueries.cpp#L22)

Call durations are not complete interaction latencies. The instrumented probe
adds logging, a heartbeat, and Qt Test. Initial absolute-timer probe runs allowed
keyboard event processing to overlap actions; those were superseded by the
sequential runs in `small-probe-v2/` and `large-probe-v2/`. Use only the sequential
results for navigation conclusions. The final runner uses the sequential approach.

### 3. Hiding stops rendering, while background polling remains

In the sequential probes, the settled hidden observation windows logged no
rendered frames. Process CPU was approximately 0.86% for the small fixture and
0.84% for the large fixture; a later small-fixture check observed 0.42%.
Memory remained allocated after visiting pages, about 357–395 MiB in the first
sequential probes. Retained memory alone is not evidence of a leak.

`GameMonitor` polls every two seconds and can invoke `nvidia-smi`, independently
of whether its page is visible. This is confirmed ongoing work, but its share of
hidden CPU has not been isolated. Decide the required background monitoring
behavior before changing it.
[GameMonitor](../src/core/session/gamemonitor.cpp#L168)

NVIDIA process monitoring returned unavailable utilization counters in a brief
attempt. A later capture missed the completed test process. There is **no reliable
per-process GPU-utilization baseline** from this session; device-wide activity
must not be attributed to Prismarine. Frame logging establishes activity, not GPU
load percentage.

## Recommended first Phase 1 slice

1. Correct the invisible indicator's animation lifecycle and add a reproducible
   regression check for idle activity.
2. Standardize the existing motion components using the
   [Qt animation research](qt-animation-research.md). Prototype shorter page/dialog
   motion and focus feedback without replacing navigation architecture.
3. Investigate the large-library reload and page-creation delays with focused
   measurements before committing to asynchronous scanning or model changes.

The evidence supports an initial acceptance criterion of **no continuous frames
when idle without an active task**. Numerical memory/latency limits remain for
review: three active-desktop runs cannot establish portable release budgets.

## Reproduction and limits

See [the runner instructions](../scripts/baseline/README.md). The diagnostic runs
do not sign in, install real content, launch Minecraft, measure complete launch
latency, validate real saves, or establish performance on other platforms.
Existing automated suites cover simulated launch/content behavior, not a physical
controller or an actual game session. No full QML profiler trace was captured;
especially the account page's 3D costs need separate investigation.

Qt documents the render-loop logging used here in its
[scene-graph documentation](https://doc.qt.io/qt-6/qtquick-visualcanvas-scenegraph.html#logging-support).
